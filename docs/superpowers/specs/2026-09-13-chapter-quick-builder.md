# Быстрый конструктор главы (admin) — Design Spec

## Контекст и решение

Текущий редактор главы (`apps/admin` → история → глава → «Редактировать содержание») уже
умеет всё, что нужно движку: пять типов узлов, связывание через `nextNodeId`, условия,
эффекты, гардероб спрайтов на персонажа. Но по итогам обсуждения с продакт-оунером (2026-09-13)
рабочий процесс сценариста сегодня слишком медленный и негибкий для того, чтобы реально
писать главы: каждая реплика — это «создать узел → открыть форму → найти в выпадающем списке
нужный ID следующего узла среди чужих UUID → сохранить → закрыть», и при этом три вещи, которые
движок уже умеет показывать игроку (фон, кто на экране и с каким выражением, отображаемое имя
персонажа), в форме узла вообще нельзя задать.

Это НЕ смена архитектуры движка чтения — модель `SceneNode`/`Condition`/`Effect` и то, как
`play_service`/`preview_service` их интерпретируют, не меняются. Это (а) добавление
недостающих полей в существующие формы узлов и (б) новый быстрый способ их создавать —
плюс два по-настоящему новых механизма, которых в движке пока нет вообще: смена отображаемого
имени персонажа по ходу истории и наряды с ценой в кристаллах и бонусом к статам, которые
выбирает игрок.

## Скоуп v1

**Входит:**
- Карточка персонажа: имя, фамилия (необязательно, только для админки), отображаемое имя,
  эмоции — редактируется в одном месте; персонажа можно создать прямо из конструктора главы.
- В форме узла «Диалог»: кто на экране + какое выражение + слева/по центру/справа; фон сцены
  (с наследованием вперёд, как уже работает у бэкенда); всё это доступно и через быстрые
  кнопки конструктора, не только через открытие формы.
- Липкая (sticky) панель быстрых кнопок над списком узлов: одна кнопка на персонажа + «Рассказчик»
  — клик сразу добавляет реплику в конец цепочки со сцеплением, без выбора ID вручную.
- Механизм «Переименовать»: смена отображаемого имени персонажа, действует с этого места и до
  следующего переименования (та же логика наследования, что у фона).
- Наряды как самостоятельная сущность на персонажа: название, цена в кристаллах (0 = бесплатно),
  бонус к статам. Кнопка «Смена наряда» в конструкторе — по выбранному персонажу собирает игроку
  экран выбора из его нарядов автоматически.
- Мини-конструктор «Выбор»: вариант ответа + (необязательно) стат и на сколько + (необязательно)
  цена в кристаллах — без отдельной формы на каждый вариант.

**Явно не входит:**
- Изменение модели условий/эффектов движка чтения — новые механизмы (имя, наряд) реализуются
  поверх неё же (см. ниже), не рядом с ней.
- Экран «Граф» и вид «Список» не убираются — остаются как есть, для сложных ветвлений
  (несколько условий, немного узлов уровня движка) быстрый конструктор не заменяет их полностью.
- Мобильное приложение и бэкенд-эндпоинты чтения (`play_service`) не меняют форму ответа —
  `staged`/`backgroundUrl` там уже есть и уже используются, спека только даёт админке способ
  их заполнять.

## Архитектура

```
apps/admin (Next.js)
  └─ Конструктор главы (новый UI поверх тех же apps/api эндпоинтов scene-nodes/choice-options)
       ├─ Быстрые кнопки → POST /admin/scene-nodes (DIALOGUE) с auto-nextNodeId у предыдущего узла
       ├─ «Переименовать» → POST /admin/scene-nodes (EFFECT), SET на скрытую переменную персонажа
       └─ «Смена наряда» → POST /admin/scene-nodes (CHOICE) + choice-options, авто-собранные из
                            каталога нарядов персонажа

apps/api (новое, минимально)
  ├─ Character: + first_name, + last_name (только для админки, никогда не идёт игроку)
  ├─ Outfit (новая таблица): character_id, key, label, price_hard, stat_effects (JSONB)
  ├─ GET/POST/PATCH/DELETE /admin/characters/{id}/outfits
  └─ play_service / preview_service: имя спикера сначала смотрит в переменную
     `__display_name` этого персонажа у игрока, и только если её нет — берёт Character.name
```

Ключевое архитектурное решение: **и «переименование», и «наряды» — не новые типы узлов
движка**, а конструкции ПОВЕРХ уже существующих EFFECT и CHOICE. Это значит: ноль изменений в
`condition_engine.py`, ноль новых типов в `SceneNodeType`, ноль риска для уже написанных и
опубликованных глав. Конструктор в админке просто скрывает от сценариста то, что за кнопкой
«Переименовать» на самом деле создаётся EFFECT-узел, а за «Сменой наряда» — CHOICE.

## Карточка персонажа

Расширяем существующую форму создания/редактирования персонажа (сейчас — только «Имя»):

```
Имя*            [ Виктор            ]
Фамилия          [ Соколов (необязательно, видна только в админке — списки/поиск) ]
Отображаемое имя [ Негодяй ] (по умолчанию = Имя; то, что видит игрок, пока не сработало
                              «Переименовать» дальше по сюжету)
Эмоции           (тот же «Гардероб», перенесён в эту карточку — было на странице истории)
```

`first_name`/`last_name` — новые поля на `Character`, `TEXT`/`LocalizedText`, только для
внутреннего использования (списки персонажей, поиск в конструкторе) — ни один игрок их не
увидит. `name` (уже существующее поле) продолжает быть «отображаемым именем» по умолчанию —
без переименований по сюжету ничего не меняется для уже написанных историй.

Персонажа можно создать, не покидая конструктор главы: кнопка «+ Новый персонаж» в панели
быстрых кнопок (см. ниже) открывает ту же карточку в компактном виде.

## Конструктор главы: панель быстрых кнопок

Над списком узлов — **закреплённая (sticky, не прокручивается вместе со страницей)** панель:

```
[Рассказчик] [Виктор] [Маша] [Паша] [+ Новый персонаж]  |  [+ Выбор] [Переименовать] [Смена наряда] [Фон]
```

- Клик по имени персонажа (или «Рассказчик») → создаёт узел «Диалог» с этим говорящим,
  автоматически ставит его `nextNodeId` предыдущему последнему узлу цепочки, сразу открывает
  текстовое поле для ввода реплики. Никакого похода в выпадающий список ID.
- Рядом с текстом реплики — быстрый выбор эмоции (только если у говорящего персонажа есть
  хотя бы одно загруженное выражение) и того, кто ещё на экране кроме говорящего (по умолчанию
  — только говорящий, по центру; можно убрать/добавить, задать позицию слева/справа).
- «Фон» — отдельная кнопка тут же: загрузить новую картинку или выбрать уже когда-то
  загруженную для этой истории. Не нажали — фон наследуется от последнего заданного выше по
  цепочке (движок уже так делает, это просто интерфейс к уже существующему полю
  `backgroundImageUrl`).
- «+ Выбор» открывает мини-конструктор (см. ниже), а не полную форму варианта на каждый пункт.
- «Переименовать» и «Смена наряда» — см. следующие разделы.

Технически: узлы по-прежнему создаются через `POST /admin/scene-nodes`, просто конструктор
сам вычисляет `order`/`nextNodeId` предыдущего узла вместо того, чтобы сценарист делал это
руками через форму. Существующие «Список»/«Граф» продолжают работать с тем же самым списком
узлов — быстрая панель ничего не меняет в данных, только в способе их создавать.

## Мини-конструктор «Выбор»

Вместо текущей вложенной формы на каждый вариант — компактная таблица прямо под узлом:

```
[Я расстроена               ] стат [drama] +[1]   цена: ( ) бесплатно (•) кристаллы [0]
[Я разочарована              ] стат [drama] +[2]   цена: ( ) бесплатно (•) кристаллы [0]
[Я зла                        ] стат [evil ] +[1]   цена: ( ) бесплатно (•) кристаллы [0]
[Я негативно отношусь к твоей…] стат [evil ] +[2]   цена: (•) бесплатно ( ) кристаллы [  ]
[+ Добавить вариант]
```

Каждая строка при сохранении превращается ровно в тот же `ChoiceOption` с `effects`, что и
сегодня (`POST /admin/choice-options`) — поле «стат» здесь по-прежнему просто текстовый ключ
переменной (заводить его отдельно не нужно, ключ появляется с первым использованием — как и
сегодня). Разница только в том, что всё видно и редактируется в одном месте, без раскрытия
каждого варианта по отдельности.

## Переименование персонажа

Кнопка «Переименовать» в панели → маленькая форма: выбрать персонажа (если в узле уже есть
говорящий — по умолчанию он) и ввести новое отображаемое имя. Сохранение создаёт EFFECT-узел
с одним эффектом:

```json
{ "variableKey": "__display_name", "characterId": "<id>", "op": "SET", "value": "Виктор" }
```

`__display_name` — служебный, скрытый от обычного использования ключ (начинается с `__`,
таблица переменных в конструкторе его не предлагает как «обычный» стат). Дальше по сюжету,
пока не встретится следующее «Переименование» этого же персонажа, его имя в репликах — то, что
сюда записано; до первого переименования — `Character.name`, как и сейчас.

**Бэкенд:** `play_service`/`preview_service` там, где сегодня для говорящего берут
`character.name`, сначала проверяют `PlayerVariableValue` по ключу `__display_name` для этого
`character_id`, и только если её нет — берут статичное имя. Это единственное изменение в
самом движке чтения во всей этой спеке; расчёт условий/эффектов не трогается вообще —
`__display_name` для условий/эффектов ничем не отличается от любой другой STRING-переменной.

## Наряды с ценой и статами

Новая таблица `outfits` (не путать с текстовым ключом наряда в `Character.sprites`, который
остаётся как есть — это по-прежнему то, что физически определяет, какой файл спрайта
показывать):

```python
class Outfit(Base, UUIDPKMixin, TimestampMixin):
    __tablename__ = "outfits"
    character_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("characters.id", ondelete="CASCADE"))
    key: Mapped[str] = mapped_column(String)          # тот же ключ, что в Character.sprites (напр. "dress")
    label: Mapped[dict] = mapped_column(JSONB)        # {"ru": "Вечернее платье"} - видит игрок
    price_hard: Mapped[int] = mapped_column(Integer, default=0)  # кристаллы, 0 = бесплатно
    stat_effects: Mapped[list] = mapped_column(JSONB, default=list)  # [{variableKey, characterId, op, value}]
```

Заводится там же, где сегодня в «Гардеробе» добавляется новый столбец-наряд («+ Добавить
наряд») — форма расширяется двумя полями (цена, статы), сам гардероб (загрузка спрайтов по
клеточкам) не меняется.

Кнопка «Смена наряда» в конструкторе главы: выбрать персонажа (с уже заполненной карточкой) →
собирает `CHOICE`-узел, где вариант на каждый наряд этого персонажа:

```
текст = outfit.label.ru
цена = { currency: "HARD", amount: outfit.price_hard }   (0 → «Бесплатно»)
effects = [ {variableKey: "outfit", characterId: <перса>, op: "SET", value: outfit.key},
            ...outfit.stat_effects ]
```

Игрок видит это как обычный узел «Выбор» (уже существующий, знакомый игрокам UI из
`play_service`/мобильного чтения) — новой механики на стороне игрока нет вообще, вся новизна —
в том, как сценарист его собирает.

## Обработка ошибок

- Переименование/смена наряда без выбранного персонажа — кнопка неактивна, а не ошибка сервера.
- Наряд без сохранённых спрайтов хотя бы в «Без наряда» — можно завести (цена/статы не зависят
  от того, загружены ли уже картинки), но конструктор предупреждает, что игрок увидит пустое
  место, пока спрайт не добавлен.
- Удаление персонажа/наряда, на который где-то в главах уже ссылается EFFECT/CHOICE — эффект
  остаётся как есть (текстовый ключ и id, не foreign key на уровне данных, ровно как сегодня
  работают обычные переменные) — движок просто не найдёт наряд/персонажа и не применит
  визуальный эффект; не 500, тихая деградация.

## Тестирование

- Backend: тесты на `Outfit` CRUD (только ADMIN/WRITER/EDITOR, как остальной контент), на
  `__display_name` — что до первого EFFECT сохраняется `character.name`, после — новое
  значение, и что оно per-player (два разных `PlayerVariableValue` для двух игроков не путаются).
- Frontend (`apps/admin`): typecheck/lint/build, как везде в этом репозитории; живая проверка
  через `orca` — собрать главу из примера продакт-оунера (Рассказчик → Маша → Иваша → Выбор на
  статы → Рассказчик-дисклеймер) кнопками панели без единого ручного выбора ID, затем то же
  самое посмотреть в «Превью».
