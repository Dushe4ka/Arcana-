# Админ-панель для сценаристов — дизайн

**Дата:** 2026-08-31
**Статус:** черновик, ожидает ревью

## Контекст и место в общем плане

Пользователь запросила две крупные новые подсистемы: личный кабинет+магазин (подписки,
докупка валюты, покупка мини-сериалов) и админ-панель для сценаристов. Это два независимых
подпроекта (разные приложения, разные пользователи, разные риски), поэтому по методичке
брейнштормим и специфицируем их по отдельности.

Согласованный порядок работы над обеими подсистемами:

0. Смена пароля — точечная задача, в любой момент параллельно с остальным.
1. **Админ-панель — этот документ.**
2. Адаптив экрана чтения и mobile-аппа под планшет/веб (отдельный этап, скилл `adapt`).
3. Спайк: способ приёма реальных платежей (Apple/Google IAP vs внешний шлюз, доступность в РФ).
4. Личный кабинет + магазин (3 подписки, докупка кристаллов, покупка мини-сериалов).
5. Опционально позже: автоматизация наполнения контента для сценаристов.

Дополнительное обоснование порядка: контентное CRUD в бэкенде уже почти полностью готово
(см. ниже), поэтому админ-панель — самая быстрая по времени большая подсистема. Плюс она
разблокирует контент для «Кинозала», который магазин из п.4 должен будет продавать. Наполнять
истории через админку можно независимо от релиза мобильного приложения в App Store/Google
Play — это два не связанных друг с другом события: истории публикуются (`status: PUBLISHED`)
через тот же backend API, который просто должен быть поднят, релиз мобильного клиента для
этого не нужен.

## Что уже готово в коде (проверено, не нужно переделывать)

- **Полное CRUD backend API для контента**, с ролями `WRITER`/`EDITOR`/`ADMIN`
  (`require_roles(...)` в `app/core/deps.py`):
  `/stories`, `/seasons`, `/chapters`, `/characters`, `/variables`, `/scene-nodes`,
  `/choice-options` — создание, правка, публикация/снятие с публикации, удаление.
- **Платные выборы уже реализованы end-to-end**: `ChoiceOption.cost_currency`/`cost_amount`,
  списание и проверка `affordable` в `play_service.submit_choice`.
- **Модель узла диалога уже поддерживает описанный автором workflow** («общее
  повествование → герой → общее»): `DialogueNodeData.speaker_character_id` (`null` =
  повествование от лица рассказчика, id — конкретный герой), `staged` (кто на сцене, позиция
  лево/центр/право), `is_thought` (мысли vs речь), `background_image_url` на узел.
- **Условия/эффекты и переменные игрока** (`VariableDefinition` + `PlayerVariableValue`,
  `Condition`/`Effect` в `app/schemas/common.py`) — движок уже умеет читать/писать
  произвольные переменные, в т.ч. привязанные к конкретному персонажу
  (`VariableDefinition.character_id`).
- Роли `WRITER`/`EDITOR`/`ADMIN` в модели пользователя — есть, но самостоятельная регистрация
  (`POST /auth/register`) всегда создаёт `PLAYER`; повышение роли — только вручную/через
  будущий экран управления пользователями.

## Чего нет вообще (новое в этой спеке)

- Самой админ-панели (фронтенда) — `apps/admin` не создан, только план в README.
- Загрузки файлов — в конфиге есть `uploads_dir`, но ни одного `UploadFile`-эндпоинта нет.
- Персистентности фона между узлами (см. ниже).
- Системы гардероба/переодеваний персонажей (см. ниже) — хотя большая часть механизма для
  неё уже случайно есть (переменные + эффекты), не хватает одного шага в резолве спрайта.
- Режима предпросмотра главы без реального сохранения прогресса/списания валюты.
- Позиции узла на холсте для графового редактора (`canvas_x`/`canvas_y`).

## Архитектура

Новое приложение `apps/admin` — Next.js (как и было заложено в README), отдельный фронтенд
поверх того же backend API, вне pnpm-turborepo контракта с `apps/mobile` (как и `apps/api`,
это самостоятельный проект — либо добавляется в pnpm workspace как обычный TS-пакет, детали
решим на этапе плана реализации). Авторизация переиспользует тот же JWT access+refresh
механизм, что и мобильное приложение — тот же `/auth/login`, те же роли в токене.

## Поток создания истории

1:1 с тем, что описал пользователь, всё уже есть в бэкенде как API-ручки:

`POST /stories` (черновик: обложка, жанр, название) → `POST /characters` на каждого
персонажа (имя, цвет подписи, спрайты по эмоциям) → сцены главы. Переключение
«общее повествование → герой → общее» в редакторе сцен — это UX-приём поверх уже
готовой схемы: выбрал персонажа как активного спикера — новые узлы подряд создаются с этим
`speaker_character_id`, пока не выбран другой или не снят выбор.

## Редактор сцен — два синхронных представления

**Референсы (опенсорс), на которые ориентируемся:**
- [Twine](https://github.com/topics/visual-novel-framework) — passage = наш `SceneNode`,
  `[[ссылка]]` = наш `ChoiceOption.next_node_id`/`ConditionNodeData.then_node_id`. Модель
  данных у нас уже 1:1 совпадает со структурой Twine.
- [Yarn Spinner](https://yarnspinner.dev/editor/) — ближе всего к требованию «оба вида
  сразу»: одни данные, но два представления (простой список для правки текста узла +
  интерактивный граф на **React Flow** для навигации/связей). Обрабатывает «сотни узлов,
  тысячи строк диалога» на этом паттерне.

**Решение:** строим оба представления одним заходом поверх одних данных, без раздельных
БД-моделей:

- **Список** — сверху вниз, форма редактирования на каждый узел (тип, текст, спикер, фон,
  спрайты на сцене; ветвления `CHOICE` — вложенные варианты внутри узла).
- **Граф** — **React Flow** (open source, MIT, активно поддерживается): узел = `SceneNode`,
  стрелка = связь `next_node_id`/`then_node_id`/`else_node_id`. Клик по узлу на графе
  открывает ту же форму редактирования, что и в списке — одна логика правки, два способа
  навигации.
- Новое поле в БД: `SceneNode.canvas_x`/`canvas_y` (nullable int) — только позиция на холсте
  графового редактора, на движок чтения не влияет.

## Загрузка файлов

Новый `POST /uploads` (multipart), сохранение на диск в уже существующий (но пока не
используемый) `settings.uploads_dir`, раздача статикой через FastAPI `StaticFiles`. При
текущем масштабе локального диска достаточно; переезд на S3-совместимое хранилище при
необходимости — замена одного модуля хранения, не переделка API-контракта.

На загрузке — сразу превью в реальных пропорциях экрана и предупреждение, если разрешение
слишком маленькое или сильно не те пропорции, чтобы проблема была видна сразу при загрузке,
а не после публикации.

## Предпросмотр перед публикацией

Отдельный «тестовый» режим прохождения главы через тот же `play_service`, что использует
мобильное приложение, но без реального `SaveSlot`/сохранения прогресса и без списания
энергии/валюты. Черновик можно проходить сколько угодно раз до `PUBLISHED`.

## Фон: персистентность между узлами + фокальная точка под адаптив

**Проблема (подтверждена чтением кода):** `background_image_url` живёт в каждом узле
отдельно, наследования между узлами нет — `play_service._build_dialogue_view` передаёт
`data.background_image_url` как есть, `null` даёт голый тёмный фон. Чтобы фон держался на
протяжении нескольких сцен, автору сейчас пришлось бы вручную проставлять его в каждом узле
— источник бага «фон съехал, забыли проставить».

**Решение:**
- Движок трактует фон как «держится, пока не сменён явно»: новое поле
  `SaveSlot.current_background_url`, обновляется при проходе узла с непустым фоном,
  подставляется как фолбэк, если у текущего узла фон не указан. Работает и при
  последовательном чтении, и при возврате к сохранению (персистентное поле, не
  пересчитывается на лету).
- В редакторе (и списке, и графе) узел, где фон явно меняется, помечается визуально — видно
  одним взглядом, какой фон действует на каком участке истории, без клика в каждый узел.
- **Фокальная точка под разные пропорции экрана** (решили закладывать сразу, не только под
  телефон): при загрузке фона — интерактивный маркер прямо на картинке, куда перетащить
  «безопасную зону» (обычно лицо/центр сцены). На стороне мобильного приложения — замена
  `Image`/`ImageBackground` (сейчас голый `react-native`, всегда центр-кроп) на `expo-image`
  с `contentPosition` (аналог CSS `object-position`, кросс-платформенно). Одна картинка +
  точка вместо отдельного файла под каждое соотношение сторон.

## Гардероб: переодевания/причёски/макияж персонажей

**Референс:** Ren'Py Layered/Attribute-система и общепринятый в жанре паттерн — «наряд» не
отдельная система, а обычная переменная состояния игрока, от которой зависит, какой спрайт
показать (не комбинаторные предрендеренные картинки на каждую пару herо×наряд, только если
комбинаций реально много).

**Что уже работает без изменений:** выбор игрока (платье/джинсы) → `ChoiceOption.effects`
пишет в `PlayerVariableValue` — заводим `VariableDefinition` (`type: STRING`, `character_id`
= привязка к конкретному персонажу, ключ например `outfit`) и выбор просто устанавливает её
значение через уже существующий механизм эффектов. Ничего нового в движке для этой части не
нужно.

**Единственный недостающий шаг:** сейчас спрайт ищется по плоскому ключу
(`sprites.get(s.sprite)` в `_resolve_staged_characters`). Меняем на составной ключ
`{наряд}_{выражение}` с откатом на плоский ключ для персонажей без гардероба (обратная
совместимость). Небольшая точечная правка в одном месте.

**В админке:** для персонажа — таблица-матрица при загрузке спрайтов (строки — выражения,
столбцы — наряды), в каждой ячейке своя картинка, с той же валидацией/превью, что и у фонов.
Причёски/макияж/аксессуары — независимые переменные-гардеробы того же типа, если по сюжету
выбираются раздельно (уточнить на этапе детального дизайна персонажей в плане реализации).

## Ограничение доступа

Доступ проверяется на уровне API (`require_roles`), не сокрытием ссылки — роль
`WRITER`/`EDITOR`/`ADMIN` выдаётся только вручную (сидинг или будущий экран управления
пользователями внутри самой админки, доступный только `ADMIN`). Публичного пути стать
сценаристом самому — нет и не появится.

## Явно не входит в эту спеку (следующие этапы плана)

- Адаптив самого экрана чтения/mobile-аппа под планшет/веб — отдельный этап (см. план выше).
- Личный кабинет, магазин, подписки, платежи — отдельная спека после спайка по платежам.
- Автоматизация наполнения контента (импорт из сценарного текста и т.п.) — опциональный
  спайк позже, после того как ручной flow обкатан.
- Детальный дизайн ролей внутри самой админки (что именно видит `WRITER` vs `EDITOR` vs
  `ADMIN`) — прорабатывается на этапе плана реализации.

## Тестирование и обработка ошибок

- Backend: новые эндпоинты (`/uploads`, preview-режим, изменение резолва спрайтов) покрываются
  так же, как остальной `apps/api` — `pytest`, `ruff check`.
- Загрузка файлов: серверная валидация типа/размера файла до сохранения на диск (не полагаться
  только на клиентскую проверку в админке).
- Предпросмотр: должен явно не иметь побочных эффектов на реальный прогресс/кошелёк игрока —
  тестируется тем, что состояние `Wallet`/`PlayerVariableValue` не меняется после
  прохождения черновика в режиме предпросмотра.
- Композитный резолв спрайта (`{наряд}_{выражение}`) — тест на откат к плоскому ключу для
  персонажей без гардероба, чтобы не сломать существующие истории.
