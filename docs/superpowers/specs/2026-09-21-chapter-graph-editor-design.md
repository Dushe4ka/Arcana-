# Chapter Graph Editor — Design Spec

## Контекст и цель

После `chapter-quick-builder` (сентябрь 2026) в редакторе главы (`apps/admin/app/(app)/stories/[id]/chapters/[chapterId]/page.tsx`) есть три способа строить контент: список узлов, липкая панель быстрых кнопок (auto-chain от «последнего по order» узла) и вкладка «Граф» (`SceneGraphView.tsx`, на `@xyflow/react`) — но граф там **только визуализирует**: рёбра читаются из данных узлов, узел можно перетащить (позиция сохраняется в `canvasX`/`canvasY`), но нельзя ни создать узел кликом по холсту, ни провести новую связь драгом.

Продукт-оунер оценил результат («уже лучше, но всё равно не то») и попросил полную переделку концепции: **граф должен стать основным конструктором** истории, с реальной поддержкой ветвления (несколько CHOICE-вариантов ведут в разные, потенциально расходящиеся и сходящиеся ветки), удобной работой с карточкой персонажа прямо в редакторе главы, и видимостью зависимостей между далёкими друг от друга главами/сезонами одной истории (переменная, заданная в С1Э5, влияет на С2Э4).

Это архитектурная переделка существующего редактора, не новый подсистема с нуля — переиспользует весь бэкенд, весь движок чтения (`condition_engine.py`, `play_service.py`, `preview_service.py`) без изменений, и почти все существующие эндпоинты `/admin/scene-nodes`, `/admin/choice-options`, `/admin/characters`, `/admin/variables`.

## Скоуп v1

**Входит:**
1. Интерактивный холст: создание узла кликом по пустому месту, соединение узлов драгом (включая «драг в пустоту» → создать+подключить новый узел за один жест), удаление отдельной связи.
2. Панель быстрых кнопок продолжает работать, но достраивает цепочку **от выбранного на графе узла**, а не от «последнего по order» — это и есть поддержка ветвления кнопками.
3. Вкладка «Персонажи» внутри редактора главы (карточка + гардероб переезжают туда со страницы истории).
4. Переключатель отображения узла графа: «История» (только говорящий+текст, +миниатюра текущей эмоции/наряда) / «Глубоко» (полная техническая сводка, как сейчас).
5. Вкладка «Переменные»: обзор всех переменных истории + список, где каждая задаётся (EFFECT/эффекты вариантов) и где проверяется (CONDITION), по всем сезонам/главам истории, с переходом («Перейти») к нужному узлу в нужной главе.

**Не входит (явно):**
- Никаких изменений в `condition_engine.py`, никаких новых типов `SceneNodeType` — все создаваемые с холста узлы идут через существующие `POST /admin/scene-nodes` / `POST /admin/choice-options`.
- Зависимости **между разными историями** — не поддерживаются и не просились; `VariableDefinition` в этой архитектуре и так уже привязана к одной истории целиком (не к главе/сезону), поэтому кросс-сезонные зависимости *внутри одной* истории работают уже сегодня на уровне данных — этому спеку нужно только сделать их видимыми и удобными для навигации.
- Система экранных эффектов (fade/скример/тряска) — отдельная, независимая тема, со своей спекой.
- Изменение способа хранения `order` в БД — поле остаётся (используется «Список»-видом как sort key и как fallback для панели кнопок), просто перестаёт быть источником истины для сцепления узлов.

## Архитектура

```
apps/admin/app/(app)/stories/[id]/chapters/[chapterId]/page.tsx  (хост, как сейчас)
├── вкладки: Список | Граф | Персонажи (новая) | Переменные (новая)
├── QuickAddToolbar.tsx        — правится: чейнит от selectedNodeId, не от order
├── SceneGraphView.tsx         — большая переработка: создание/соединение узлов
│   └── новые под-компоненты: NodeTypeMenu (меню выбора типа при клике/драге в пустоту)
├── CharactersPanel.tsx        — новый компонент-обёртка: переиспользует
│   CharactersSection (со страницы истории) + WardrobeMatrix как есть
└── VariableReferencesPanel.tsx — новый компонент: список переменных + переходы

apps/api/app/routers/variables.py            — новый эндпоинт (см. ниже)
apps/api/app/services/variable_usage_service.py  — новый сервис, обходит узлы истории
```

## 1. Интерактивный холст

**Типы узлов и их выходы** (соответствуют полям, которые движок уже читает):

| Тип узла | Выходы | Поле, которое пишется |
|---|---|---|
| DIALOGUE, EFFECT | 1 («далее») | `data.nextNodeId` |
| CONDITION | 2 («да» / «нет») | `data.thenNodeId` / `data.elseNodeId` |
| CHOICE | N (по одному на вариант, динамически) | `nextNodeId` конкретного `ChoiceOption` |
| END | 0 | — |

CHOICE рендерится собственным React Flow custom-node-компонентом (стандартный паттерн `@xyflow/react` — несколько именованных `<Handle>` на одном узле), с одним выходом на каждый текущий вариант; при добавлении/удалении варианта в панели редактирования узла набор выходов у него на графе пересчитывается сам при следующей отрисовке.

**Жесты:**
- **Клик по пустому месту холста** → открывается `NodeTypeMenu` рядом с точкой клика: объединяет весь уже существующий в редакторе словарь создания узлов в одном месте — быстрые кнопки `QuickAddToolbar` (Рассказчик, кнопка на каждого персонажа истории, «+ Новый персонаж») и общие типы узлов, сегодня создаваемые через отдельный ряд «+ Тип» на вкладке «Список» (`onCreateNode`, по `NODE_TYPE_LABELS`: Диалог/Выбор/Условие/Эффект/Конец) — выбор создаёт **несвязанный** узел в этой точке (`canvasX`/`canvasY` = координаты клика).
- **Драг от выхода узла на другой существующий узел** → создаётся связь: `PATCH` соответствующего поля (таблица выше) на id узла-цели.
- **Драг от выхода в пустое место** → открывается тот же `NodeTypeMenu`; после выбора типа — создаётся новый узел **и сразу** подключается (`POST` узла, затем `PATCH` источника) — один жест вместо двух отдельных действий.
- **Клик по связи (ребру)** → появляется кнопка/крестик удаления этой конкретной связи (`PATCH` соответствующего поля в `null`). Узлы по-прежнему нельзя удалить случайным нажатием Delete (`deleteKeyCode={null}` остаётся) — защита распространяется только на узлы, не на рёбра, иначе перестроить ветвление станет неудобно.
- Висящая связь на несуществующий узел (например, целевой узел удалили) не считается ошибкой — по общей конвенции этого проекта (см. `chapter-quick-builder`'s "тихая деградация") просто не рисуется на графе; React Flow и так не рендерит ребро без обеих сторон.

## 2. Панель быстрых кнопок: чейнинг от выбранного узла

`onAddDialogue`/`onRename`/`onChangeOutfit` (и их общий `chainNodeForward`) сегодня вычисляют «предыдущий последний узел» через `nodes.sort(order).at(-1)`. Меняется правило:

- Если на графе **выбран** узел (`selectedNodeId` из `SceneGraphView`, поднятый в `page.tsx`) — новый узел от кнопки чейнится **от него**, вне зависимости от order. Это и есть работа с ветвлением через кнопки: встал на нужный узел дерева → нажал кнопку → реплика встроилась именно сюда.
- Если ничего не выбрано (например, только открыли главу, ещё ни разу не кликали по графу) — поведение как сегодня: чейнится от последнего по order узла. Сохраняет привычный «просто жму кнопки подряд» сценарий для линейных участков истории без необходимости сначала что-то выбирать.
- После создания через кнопку новый узел становится выбранным (как сейчас) — так что серия кликов по кнопкам без ручного выбора продолжает работать линейно, а один клик по узлу на графе перед следующим кликом кнопки — ветвит.

## 3. Панель «Персонажи» в редакторе главы

Новая вкладка, третья по счёту. Показывает ровно то, что сегодня показывает `CharactersSection` на странице истории (создание персонажа, Имя/Фамилия/Отображаемое имя/Главная героиня, `WardrobeMatrix` с ценами и бонусами наряда) — компоненты переиспользуются как есть, просто рендерятся в новом месте с теми же пропсами (`storyId`, список персонажей, колбэк обновления). Страница истории (`stories/[id]/page.tsx`) на первом этапе может оставить укороченный ростер персонажей со ссылкой «редактировать → открой любую главу», либо просто убрать раздел — конкретика фиксируется в плане, не принципиальна для этой спеки.

## 4. Режим отображения узла: «История» / «Глубоко»

Переключатель над холстом (persist в `useState`, не в БД — это личная настройка сессии автора, не свойство главы). Влияет только на то, что рендерит `SceneGraphView` как подпись узла:

- **История**: имя говорящего (или «Рассказчик») + текст реплики (обрезанный), плюс маленькая миниатюра текущей эмоции/наряда персонажа **на этот момент истории** — вычисляется как «последний staged/наряд для этого персонажа, встреченный при обходе цепочки от начала до этого узла» (не за весь граф — если персонаж переоделся раньше по одной ветке, но не по другой, показываем то, что актуально именно на пути к этому узлу; для узла с несколькими входящими путями — берём любой один валидный путь, это подсказка для автора, не точный рантайм-расчёт).
- **Глубоко**: как сегодня, `nodeSummary()` без изменений (тип узла, полная техническая сводка).

Переключение мгновенное (просто разные пропсы в функцию сборки подписи узла), не требует перезапроса данных.

## 5. Вкладка «Переменные»: обзор + переход

**Новый бэкенд-эндпоинт** `GET /admin/stories/{storyId}/variable-usages` (ADMIN/WRITER/EDITOR, как весь остальной контент-API):

```json
[
  {
    "definition": { "id": "...", "key": "spared_villain", "label": {"ru": "Пощадил злодея"}, "characterId": null },
    "usages": [
      {"chapterId": "...", "chapterTitle": {"ru": "..."}, "seasonIndex": 1, "chapterIndex": 5,
       "nodeId": "...", "nodeType": "EFFECT", "role": "sets"},
      {"chapterId": "...", "chapterTitle": {"ru": "..."}, "seasonIndex": 2, "chapterIndex": 4,
       "nodeId": "...", "nodeType": "CONDITION", "role": "reads"}
    ]
  }
]
```

Реализация — новый сервис (`variable_usage_service.py`), который загружает **все** узлы истории (по всем сезонам/главам) и на стороне Python обходит `data` каждого узла (эффекты EFFECT-узлов, `visibleWhen`/эффекты вариантов CHOICE, `condition` CONDITION-узлов — включая вложенные группы AND/OR), собирая `(variableKey, characterId)` → список ссылок с ролью `sets`/`reads`. Не через JSONB SQL-запрос — формы `data` слишком разные между типами узлов, обход в Python проще и надёжнее. Для типичного объёма узлов на историю (сотни, не миллионы) — не проблема по производительности; при реальной необходимости оптимизации это можно позже закешировать, не меняя контракт эндпоинта.

**UI**: список переменных (можно сгруппировать по «общая характеристика» / «привязана к персонажу X», как уже делает `VariableDefinition.characterId`), у каждой — таблица использований с сезоном/главой/типом узла/ролью. Кнопка **«Перейти»** у каждой строки открывает `stories/[id]/chapters/[chapterId]?view=graph&node={nodeId}` — граф той главы, с уже выбранным (и проскроленным в вид, `fitView`/`setCenter` у `@xyflow/react`) этим узлом.

Ничего не пишется — эндпоинт полностью read-only, движок чтения не трогается.

## Обработка ошибок

- Соединение драгом на узел неправильного типа (например, пытаться подключить второй выход у DIALOGUE) — невозможно на уровне UI: у DIALOGUE/EFFECT рендерится ровно один хэндл, тянуть больше неоткуда.
- Драг, брошенный не на узел и не на пустое место (например, за пределы холста) — React Flow сам отменяет соединение, ничего не отправляется на бэкенд.
- Удаление персонажа/наряда, на который ссылается уже созданный узел — не меняется: как и в `chapter-quick-builder`, тихая деградация на уровне чтения, не 500.
- Пустая история без ни одной `VariableDefinition` — вкладка «Переменные» показывает пустое состояние с подсказкой, не ошибку.

## Тестирование

- `apps/api`: TDD на новый эндпоинт `variable-usages` — тест на сбор `sets`/`reads` через несколько глав/сезонов одной истории, тест на пустую историю, тест на вложенные AND/OR группы условий.
- `apps/admin`: без раннера тестов (как весь проект) — verification: typecheck/lint/build + живой прогон через `orca`:
  - воспроизвести ровно пример продукт-оунера: CHOICE с вариантом 1 и вариантом 3, ведущими в разный текст и разное дальнейшее ветвление, построенный **только жестами на холсте** (клик по пустому месту + драг для соединений), без единого захода в «Список»;
  - создать переменную в главе одного сезона, проверить её в главе другого сезона того же сезона/истории, убедиться что вкладка «Переменные» видит оба места и «Перейти» реально открывает нужный узел;
  - переключить «История»/«Глубоко» и убедиться, что миниатюра эмоции/наряда в «Истории» соответствует тому, что реально проиграется в этой точке (сверить с «Превью»).
- `critique`/`polish` — обязательны для холста, меню выбора типа узла и вкладки «Персонажи» (это самая заметная визуальная переделка во всём проекте на сегодня).
