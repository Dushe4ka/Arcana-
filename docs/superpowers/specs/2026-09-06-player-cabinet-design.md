# Личный кабинет игрока (сайт) — Design Spec

## Контекст и решение

Личный кабинет (статы, магазин, подписки, покупка валюты) изначально рассматривался как
экран внутри мобильного приложения. По итогам обсуждения (2026-09-06) решено вынести его на
**отдельный сайт**, куда приложение только даёт ссылку — минимум интерфейса оплаты внутри
самого приложения:

- **Обходит найденную в платёжном спайке серую зону с Apple.** Правило 3.1.1 требует
  собственный In-App Purchase Apple для цифрового контента, покупаемого *внутри* приложения.
  Если весь интерфейс оплаты живёт вне приложения (пользователь физически покидает
  приложение в системный браузер), это тот же паттерн, что использует Kindle/Netflix/Spotify
  для легального обхода этого требования. Не 100% гарантия неприкосновенности от ревью, но
  кардинально ниже риск, чем строить оплату внутри приложения.
- Не задевает RuStore вообще — там ограничение только на использование чужого платёжного SDK
  *внутри* приложения, к чистой внешней ссылке вопросов нет.
- Более удобная поверхность для табличных/графических данных (линии отношений, история), чем
  экран мобильного приложения.
- Переиспользует стек `apps/admin` (Next.js + Tailwind) — не новая технология для команды.

Полный обзор платёжного ландшафта (почему Google Play исключён полностью, почему Apple IAP
сейчас не работает для RU, почему RuStore + ЮKassa — рабочий путь) — см. память
`arcana-payments-provider-decision` (зафиксирована по итогам спайка 2026-09-05), сюда не
дублируется.

**Статус реализации (на 2026-09-06):** вся бэкенд-часть уже реализована и покрыта тестами
(ветка `player-cabinet-backend`): `POST /auth/cabinet-link-token`, `POST /auth/cabinet-exchange`,
`GET /me/stats`, `GET /me/purchases/packages`, `POST /me/purchases`, `POST /webhooks/yookassa`,
таблицы `cabinet_link_tokens` и `purchases`, клиент ЮKassa. Разделы «Данные: вкладка статов»,
«Покупка валюты», бэкенд-часть «Потока входа» ниже описывают уже готовый код (оставлены для
контекста). Следующий план реализует **только**: сайт `apps/cabinet` и точку входа в
`apps/mobile`.

**Обновление (на 2026-09-08):** сайт (`apps/cabinet`) и точка входа в `apps/mobile` реализованы.
Осталось: получить sandbox-ключи ЮKassa и прогнать живой цикл оплата → webhook → зачисление
валюты, а также продакшн-деплой `apps/cabinet`.

## Скоуп v1 (осознанно урезан)

**Входит:**
- Просмотр баланса кошелька (soft/hard/энергия/уровень — уже есть на бэкенде).
- Вкладка статов: линии отношений (переменные, привязанные к персонажу) + прочие переменные
  сюжета, сгруппированные по историям, где у игрока есть прогресс.
- Покупка HARD-валюты за рубли через ЮKassa (фиксированный список пакетов).
- Вход на сайт **только** через диплинк из приложения (одноразовый код → сессия). Отдельной
  формы логина на сайте в v1 нет.
- **Точка входа в приложении (`apps/mobile`):** на карточке «Кошелёк» в профиле — кнопка
  «Пополнить кристаллы» и строка-ссылка «Личный кабинет и статистика». Обе получают
  одноразовый код (`POST /auth/cabinet-link-token`) и открывают
  `${EXPO_PUBLIC_CABINET_URL}/auth/callback?code=<код>` через `Linking.openURL` (системный
  браузер, не `WebBrowser`/WebView — пользователь должен физически покинуть приложение, тот
  же Apple-риск, что и в потоке входа ниже). Общий хелпер `apps/mobile/lib/cabinet.ts`, чтобы
  не дублировать логику. Новый env `EXPO_PUBLIC_CABINET_URL`.

**Явно не входит (следующие этапы):**
- Подписки (3 тарифа) — нужна отдельная модель тарифов/доступа, которой пока нет на бэкенде;
  отдельная спека после того, как v1 обкатан.
- Покупка мини-сериалов за валюту/рубли — контента такого типа ещё не существует в модели
  историй.
- Магазин уже-в-истории платных выборов (это разные вещи: `ChoiceOption.cost*` уже работает
  внутри самого чтения, к личному кабинету не относится).
- Отдельный вход на сайт по email/паролю без приложения.
- Диплинк обратно в приложение после оплаты — баланс в приложении обновится при следующем
  обращении к `GET /wallet` (обычно открытие приложения/экрана кошелька), без искусственного
  форсирования. Если это ощутимая проблема на практике — добавить позже, не блокирует v1.
- Смена пароля (упомянута в исходном раннем брейншторме) — это функция аккаунта, не привязана
  к сайту конкретно, может жить и в приложении; выносится в отдельное обсуждение.

## Архитектура

```
Mobile App ──(диплинк с одноразовым кодом)──▶ apps/cabinet (новый сайт) ──▶ apps/api ──▶ PostgreSQL
                                                      │
                                                      └──▶ ЮKassa (хостед-чекаут + вебхук)
```

Новый пакет `apps/cabinet` — Next.js (App Router) + Tailwind 4, стек один-в-один с `apps/admin`
(Next 16.3.4, React 19, `@arcana/shared`, eslint-config-next), отдельный деплой. Копирует
уже отработанный в `apps/admin` набор решений (структура `app/`, конвенции ошибок из
`lib/api.ts`), но с принципиальными отличиями:

- **Токены сессии — httpOnly / Secure / SameSite=Lax cookie**, выставляемые Next.js route
  handler'ом на сервере, а не `localStorage` (как у админки) — сайт публичный, поверхность
  атаки шире, чем внутренний инструмент для команды из нескольких человек. Клиентский JS
  токены не видит.
- **`lib/api.ts` работает на сервере** (server components + route handlers): читает токены
  из cookie через `next/headers`, ходит в `apps/api`. При `401` один раз дёргает
  `POST /auth/refresh`, пишет новую пару токенов в cookie (`cookies().set(...)`), повторяет
  запрос; если refresh не удался — чистит cookie и редиректит на `/session-expired`. Нет
  zustand — состояние сессии целиком в cookie.
- **Нет формы логина/пароля вообще в v1** — единственный способ получить сессию — обменять
  диплинк-код.
- **Локализуемый текст контента** (`LocalizedText`) рендерится по ключу `ru`, как в
  mobile/admin.

### Страницы

| Маршрут | Тип | Делает |
|---|---|---|
| `/auth/callback?code=…` | server route handler | `POST /auth/cabinet-exchange` → токены в cookie → `redirect('/')`. Невалидный/просроченный/использованный код → `redirect('/session-expired')` |
| `/` | server component | Баланс кошелька (`GET /wallet`): монеты / кристаллы / энергия / уровень + карточки-ссылки на «Магазин» и «Статы» |
| `/shop` | server component + client-кнопки | Пакеты из `GET /me/purchases/packages`. «Купить» → внутренний route handler `POST /api/checkout` → `POST /me/purchases` → полный редирект браузера на `confirmationUrl` (не iframe — рекомендация ЮKassa) |
| `/wallet?purchase=…` | client component | `return_url` от ЮKassa. «Обрабатываем платёж», поллит `GET /wallet` каждые ~2 с, стоп при изменении баланса или через ~30 с («баланс обновится позже», без бесконечного спиннера) |
| `/stats` | server component | `GET /me/stats` → по историям с прогрессом: линии отношений (прогресс-бары по `minValue`/`maxValue`) + общие переменные |
| `/session-expired` | статическая | «Ссылка недействительна — откройте личный кабинет в приложении заново» |

### Визуальное направление

Сайт делается в эстетике мобильного приложения Arcana (тёмная мистическая палитра, Playfair
Display для заголовков, акценты монеты/кристаллы/энергия из `apps/mobile/lib/theme.ts`) —
пользователь не должен чувствовать, что попал «куда-то не туда». Конкретную типографику и
палитру задать через скилы `frontend-design` + `ui-ux-pro-max` на этапе реализации, финальный
проход — `critique` + `polish`.

### Что не в этом плане

- **Деплой** (регистрация домена `cabinet.arcana.app`, прод-хостинг, CI) — отдельная
  ops-задача. Этот план — локальная разработка (порт **3100**) + сборка/линт/typecheck.
- **Живой прогон оплаты через ЮKassa** — до получения sandbox-ключей (см. «Разработка/
  тестирование»). Код готов их принять через env; в тестах встречный запрос к API ЮKassa
  замокан.

## Поток входа (диплинк-хендшейк)

1. Мобильное приложение (уже авторизовано обычным JWT access-токеном) вызывает новый
   бэкенд-эндпоинт `POST /auth/cabinet-link-token`. Бэкенд генерирует одноразовый непрозрачный
   код, хранит **хэш** кода (не сам код) в новой таблице `cabinet_link_tokens` с TTL 60 секунд
   — та же схема хранения, что уже используется для refresh-токенов (`refresh_tokens`), просто
   с гораздо более коротким временем жизни и полем "потрачен" вместо ротации.

   ```python
   class CabinetLinkToken(Base, UUIDPKMixin):
       __tablename__ = "cabinet_link_tokens"
       user_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("users.id", ondelete="CASCADE"))
       token_hash: Mapped[str] = mapped_column(String)
       expires_at: Mapped[datetime] = mapped_column(DateTime(timezone=True))
       used_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True), nullable=True)
       created_at: Mapped[datetime] = mapped_column(DateTime(timezone=True), default=_utcnow)
   ```

2. Приложение открывает `https://cabinet.arcana.app/auth/callback?code=<код>` через
   `Linking.openURL` (системный браузер, не встроенный WebView — важно для того же
   Apple-риска: пользователь должен физически покинуть приложение, а не остаться в
   контролируемом приложением окне).
3. `apps/cabinet`'s `/auth/callback` — server-side route handler (не клиентский JS) вызывает
   `POST /auth/cabinet-exchange` с кодом. Бэкенд: находит токен по хэшу, проверяет
   `expires_at`/`used_at IS NULL`, атомарно помечает `used_at`, выдаёт обычную пару
   access+refresh JWT для этого пользователя (тот же механизм, что уже используется при
   логине).
4. Route handler кладёт токены в httpOnly cookie, редиректит на `/` (главная страница
   кабинета — баланс + ссылка на статы/магазин).
5. Код одноразовый и живёт 60 секунд — повторное открытие той же диплинк-ссылки ведёт на
   страницу "ссылка недействительна, вернитесь в приложение и откройте личный кабинет заново".

## Данные: вкладка статов

Новый read-only эндпоинт `GET /me/stats` (роль `PLAYER`, как и остальные `/me`-подобные вещи).
Агрегирует по каждой истории, где у игрока есть `SaveSlot` (т.е. есть прогресс — не
показываем статы по историям, которые игрок не начинал):

```python
class RelationshipStatOut(CamelModel):
    character_id: str
    character_name: LocalizedText
    character_name_color: str
    variable_key: str
    label: LocalizedText
    value: float | bool | str
    min_value: float | None
    max_value: float | None

class GeneralStatOut(CamelModel):
    variable_key: str
    label: LocalizedText
    value: float | bool | str

class StoryStatsOut(CamelModel):
    story_id: str
    story_title: LocalizedText
    relationships: list[RelationshipStatOut]
    general: list[GeneralStatOut]

# GET /me/stats -> list[StoryStatsOut]
```

`relationships` — переменные с непустым `character_id` (линии отношений, естественно
ложатся на прогресс-бар через `min_value`/`max_value`, уже существующие в модели). `general`
— остальные переменные той же истории (флаги сюжета, счётчики без привязки к персонажу).
Значения — `PlayerVariableValue`, с откатом на `default_value`, если игрок ещё не менял
переменную (тот же паттерн, что уже в `variables_service.load_context`, только не для
движка условий, а для отдачи наружу).

## Покупка валюты

Новая таблица `Purchase` (учёт платежей, не только для истории/аудита, но и как источник
истины для идемпотентности вебхука):

```python
class Purchase(Base, UUIDPKMixin, TimestampMixin):
    __tablename__ = "purchases"
    user_id: Mapped[uuid.UUID] = mapped_column(ForeignKey("users.id", ondelete="CASCADE"))
    currency: Mapped[CurrencyCode] = mapped_column()  # только HARD в v1
    amount: Mapped[int] = mapped_column(Integer)       # сколько валюты зачислить
    price_rub_kopecks: Mapped[int] = mapped_column(Integer)
    provider: Mapped[str] = mapped_column(String, default="yookassa")
    provider_payment_id: Mapped[str] = mapped_column(String, unique=True)
    status: Mapped[PurchaseStatus] = mapped_column()  # PENDING/COMPLETED/FAILED/CANCELED
    completed_at: Mapped[datetime | None] = mapped_column(DateTime(timezone=True), nullable=True)
```

Пакеты валюты — фиксированный список констант на бэкенде (не сложная система прайсинга),
пример (точные цифры утверждает бизнес, это иллюстрация):

```python
CURRENCY_PACKAGES = [
    {"id": "hard_100", "currency": "HARD", "amount": 100, "price_rub_kopecks": 14900},
    {"id": "hard_550", "currency": "HARD", "amount": 550, "price_rub_kopecks": 74900},
    {"id": "hard_1200", "currency": "HARD", "amount": 1200, "price_rub_kopecks": 149000},
]
```

Поток:
1. `GET /me/purchases/packages` — отдаёт список пакетов (для рендера магазина на сайте).
2. `POST /me/purchases` `{packageId}` → бэкенд создаёт `Purchase` (status=PENDING), создаёт
   платёж через REST API ЮKassa (`POST https://api.yookassa.ru/v3/payments`, `confirmation.type:
   "redirect"`, `return_url` указывает обратно на `/wallet?purchase=<id>` кабинета), сохраняет
   `provider_payment_id`, отдаёт сайту `confirmation_url`.
3. Сайт делает полный редирект браузера на `confirmation_url` (не iframe — так рекомендует
   сама ЮKassa).
4. ЮKassa шлёт вебхук `POST /webhooks/yookassa` на событие `payment.succeeded`. **Бэкенд не
   доверяет телу вебхука напрямую** (типовая рекомендация для платёжных интеграций, не только
   для ЮKassa) — по `object.id` из вебхука делает встречный GET-запрос к API ЮKassa
   (`GET /v3/payments/{id}`) своим секретным ключом, чтобы получить статус из первоисточника, а
   не из потенциально подделываемого тела запроса. Если статус реально `succeeded` и
   соответствующая `Purchase.status == PENDING` — начисляет валюту через уже существующий
   `wallet_service.grant_currency(user_id, currency, amount, reason=f"yookassa:{payment_id}")`
   и переводит `Purchase.status = COMPLETED`. Если `Purchase` уже `COMPLETED` — no-op (защита
   от повторной доставки вебхука).
5. Сайт на `/wallet?purchase=<id>` после возврата с оплаты показывает "обрабатываем платёж" и
   опрашивает `GET /wallet` с интервалом, пока баланс не изменится или не истечёт разумный
   таймаут (~30 сек) — после которого показывает "если платёж прошёл, баланс обновится через
   некоторое время" вместо бесконечного спиннера.

**Разработка/тестирование:** ЮKassa даёт тестовый магазин (sandbox shopId + тестовые ключи) —
интеграция и тесты идут через него, реальные боевые ключи ЮKassa подключает бизнес отдельно
перед запуском, это не то, что можно получить или сконфигурировать в рамках реализации.

## Обработка ошибок

- Диплинк-код невалиден/истёк/уже использован → страница с понятным сообщением и инструкцией
  вернуться в приложение (не голый 401).
- Создание платежа у ЮKassa упало (сеть, невалидный ключ и т.п.) → `Purchase` не создаётся
  вовсе (или создаётся и сразу помечается FAILED), пользователю — понятная ошибка "не удалось
  начать оплату, попробуйте позже", не техническая деталь.
- Вебхук с `provider_payment_id`, которого нет в `Purchase` — логируется и игнорируется (`200
  OK` всё равно нужно вернуть ЮKassa, чтобы она не повторяла попытки бесконечно), не 500.

## Тестирование

- Backend: `pytest` (по конвенции `apps/api`) — код диплинка (валиден/просрочен/уже
  использован/чужому пользователю), `/me/stats` (относится только к историям с прогрессом,
  верно делит relationships/general), вебхук ЮKassa (идемпотентность на повторной доставке,
  неизвестный payment_id не роняет 500, реальный статус берётся через встречный запрос к
  ЮKassa API, замоканный в тестах, а не из тела вебхука).
- Frontend (`apps/cabinet`): typecheck/lint/build по конвенции `apps/admin`; живая проверка
  через `orca` в процессе реализации (доступен в этой среде), включая полный проход
  диплинк-хендшейка на сидированных данных (`seed.py`). Проход оплаты доводится до полного
  редиректа на `confirmation_url`; сам платёж на стороне ЮKassa и доставка вебхука —
  отдельным follow-up после подключения sandbox-ключей (бэкенд-тесты вебхука уже мокают
  встречный запрос к API ЮKassa).
